# 常见问题

## 这个工具做不到什么

先把边界说清楚，比说功能更重要。

| 做不到 | 为什么 | 有没有替代 |
| --- | --- | --- |
| 强制把你从游戏里踢出去 | 没有无障碍权限就发不了返回键。而且这不是本项目的目标 | 卡片上的按钮会把面板推给你，决定还是你做的 |
| 按 0 延迟拦截“游戏刚启动的那一帧” | `UsageStatsManager` 的事件是异步写入的，通常有 0.5–2 秒延迟 | 用加载画面那几秒作为窗口，实测够用 |
| 在别人隐藏悬浮窗的应用上弹卡片 | Android 12 起应用可以调 `setHideOverlayWindows(true)` 屏蔽所有非系统悬浮窗 | 无。银行类、部分游戏可能会这样 |
| 识别工作资料（Work Profile）里的应用 | 跨用户查询使用情况在普通应用权限下不可行 | 无 |
| 在分屏时同时跟踪两个应用 | 前台应用的语义在分屏下本身就不唯一 | 只会跟上其中一个，文档里说明 |
| 保证在所有国产 ROM 上都活着 | 厂商的后台清理策略不公开、且逐版本变化 | 权限页里有跳转，需要在各家真机上实测 |

## 用户会问的

**为什么不给通知权限也能跑？那不是绕过系统限制吗？**

不是绕过。前台服务的生命周期本来就不受 `POST_NOTIFICATIONS` 约束，这是 Android 13 的设计：
通知权限决定的是“通知可不可见”，不是“服务能不能跑”。
但服务本身仍然会在系统的“正在运行 / 活跃应用”界面里被列出来，
所以“完全无感”做不到，最多做到“无声、无振动、通知栏不显示”。README 里对用户就是这个说法。

**为什么“悬浮窗”权限是必需的？听起来只是用来弹窗的。**

不是。从 Android 15 起，目标 SDK 35 的应用必须**已经持有一个可见的悬浮窗**，
才被允许从后台启动前台服务；而悬浮窗权限同时还是“允许从后台启动 Activity”的豁免条件之一
（“退出”按钮就靠它）。所以这个权限在这里是后台存活和主动退出的技术前提，不只是显示卡片。

**为什么统计里看不到“我今天刷了多久小红书”？**

因为刻意不记。`StatsStore` 只保存次数和总时长，不记录应用名和时间点。
这样即使手机被别人拿到，这份数据也说明不了任何具体行为。
如果你觉得“每个应用分别记”更有用，那是另一个产品决策，需要重新想隐私代价。

**预设名单里的包名对不上怎么办？**

`PresetCatalog` 里的包名是尽力而为的：应用改版、换渠道包、改名都会让它失效。
所以匹配逻辑同时看包名和应用显示名，并且分类页永远以“本机实际安装列表”为准，
“一键套用预设名单”会先与本机列表求交集，只套用真正存在的那部分。
发现对不上的，直接提 issue 附上 `adb shell pm list packages | grep 关键词` 的输出。

**为什么阈值最短只能设 1 分钟？**

再短就变成骚扰了。这个工具的定位是“可能走神时问一次”，不是秒表。

**为什么提醒触发了但屏幕上看不到？**

先把"触发"和"显示"分开：`本地记录` 里的提醒次数来自策略引擎，它只能说明"该提醒了"；
卡片有没有真的出现在屏幕上，是另一件事。这两件事之间有三个可能断掉的环节：

1. **没有悬浮窗权限** → `showCard()` 直接返回，窗口压根没建。
2. **`addView()` 抛异常** → 窗口被系统拒绝。
3. **`addView()` 成功但窗口不可见** → 最阴的一种。`addView` 不抛异常不代表窗口对用户可见，
   厂商 ROM 完全可以把窗口加进 WindowManager 之后立刻隐藏。

**本项目在 0.1.1 之前踩过第 3 种的变体**：卡片 root 的 alpha 初始值是 0，靠一个
`View.animate()` 动画把它升到 1。已经反复有人报告"加到 WindowManager 上的 View，
其动画不保证会跑"；一旦动画没跑（后台进程被压帧率、或动画的 run queue 没被 flush），
卡片就永远停在 alpha=0 —— 表现为"提醒触发了，屏幕上什么都没有，logcat 也没有报错"。
现在 alpha 直接就是 1，动画只作为可见之后的修饰，删掉它也不影响功能。
**改这块代码时不要退回"靠动画变可见"的写法。**

现在这三种情况都能在应用内「诊断」页看到：`Card` 标签那几行会写明
`showCard -> ADDED/NO_PERMISSION/FAILED`，以及 700ms 后回查到的
`attached=? visibility=? size=WxH`。三种情况都不会再让提醒丢失——加不上或不可见时
自动降级成一条带同样选项的横幅通知。

**ColorOS / MIUI 这类 ROM 还要额外注意什么？**

它们把"悬浮窗"和"后台弹出界面"拆成了两个独立开关，两个都要开；另外"锁定后台"只影响
进程被杀，不解决悬浮窗被拦。如果前台自检能弹、后台就是不弹，那就是该 ROM 拦了后台悬浮窗——
这是它的设计选择，应用层绕不过去，降级通知是唯一可靠的替代路径。

**降级通知为什么只是通知栏里一条安静的记录，不弹横幅？**

大概率是踩了这个坑：**给通知调了 `setSilent(true)`。**

官方 `NotificationCompat.Builder` 文档原文：

> `setSilent(boolean silent)` — If `true`, silences this instance of the notification
> **and prevents the notification from peeking on screen, regardless of the importance,
> sounds, or vibrations set on the notification or notification channel.**

也就是说，哪怕把通道设成 `IMPORTANCE_HIGH`，只要通知上带了 `setSilent(true)`，它就**永远不会**
以横幅形式弹出。在国产 ROM 上这会进一步被归到「静默通知」分组里折叠起来，
表现就是"通知中心里只有一个小图标"。

正确做法是**让通道无声音，而不是让通知静音**：

```kotlin
// 通道：会弹横幅，但不会响
NotificationChannel(id, name, NotificationManager.IMPORTANCE_HIGH).apply {
    setSound(null, null)
    enableVibration(false)
    enableLights(false)
}

// 通知：不要 setSilent(true)
builder.setPriority(NotificationCompat.PRIORITY_HIGH)
```

`zhizhi_monitor`（前台服务常驻通知）反过来——它是 `IMPORTANCE_MIN` 且**应该**带
`setSilent(true)`，因为我们从来不希望它弹出来。

另外注意：**通道的重要性只在创建时生效，之后改代码没用。** 用户或 ROM 把它降下来之后，
只能由用户在系统设置里改回去。所以诊断页会把通道的真实重要性显示出来。

**为什么游戏提醒会慢一两秒？**

`UsageStatsManager` 的事件是异步写入的，从应用切到前台到我们能读到通常有 0.5–2 秒延迟。
再叠加轮询间隔：0.1.2 之前时段内是 2.5 秒，所以最坏情况要 4 秒以上才识别到，玩家已经进局了。
现在时段内固定 1 秒轮询，总延迟压到 ~2 秒。

这是系统限制，不是可以消掉的 bug。想让"游戏启动即确认"做到 0 延迟，只能上无障碍服务，
而那正是本项目明确拒绝的东西。

**为什么同一个应用第二次进来就不提醒了？**

几乎一定是**回答冷却**在起作用，不是 bug。

设计意图：用户刚在卡片上点过"我走神了，退出"，如果 30 秒后重新进来又立刻被问一遍，
那就是骚扰。所以任何一次回答（已完成退出 / 我走神了 / 游戏算了）都会让**该应用**进入一段冷却期。

0.1.4 之前这个问题特别容易被误判成故障，因为冷却值是写死的、界面上看不到：
退出后 **10 分钟**、游戏取消后 **5 分钟**——用户反复测试同一个应用时会觉得"第二次根本不弹"。

现在它是首页「提醒节奏」里的**「回答之后的冷却时间」**滑杆，范围 0–10 分钟，默认 **2 分钟**，
设成 0 就是每次都问。游戏前确认本身也受它约束。

（另外还有一层独立的抑制：点过「别再提醒这个应用」之后，该包在本次运行内不会再被提醒，
并且会被写进忽略名单——这是永久的，不是冷却。）

## 开发者会问的

**为什么所有悬浮窗操作都是 suspend 函数？**

因为 `WindowManager.addView()` **必须在主线程调用**。它内部会构造 `ViewRootImpl`，
而 `ViewRootImpl` 的构造函数会创建一个绑定**当前线程** Looper 的 `Handler`。
在工作线程（比如 `Dispatchers.Default`）上调它，会直接抛：

```
RuntimeException: Can't create handler inside thread
Thread[DefaultDispatcher-worker-7,5,main] that has not called Looper.prepare()
```

这个坑在本项目里藏了很久，而且伪装得极好：**Service 的生命周期回调（`onCreate`/`onStartCommand`）
本来就在主线程，所以"在应用内点测试卡片"永远成功；而监测主循环跑在 `Dispatchers.Default` 上，
所以"从后台弹卡片"永远失败。** 这个组合让人很自然地得出"厂商 ROM 拦截了后台悬浮窗"的错误结论，
然后花好几轮去查系统权限。

所以 `OverlayController` 的公开 API 一律是 suspend 的，内部自己
`withContext(Dispatchers.Main.immediate)` 切主线程。**调用方不要绕开它**，
也不要在非主线程直接碰 `View` / `WindowManager`。少数必须在主线程同步完成的地方
（`startForeground` 之前要先挂好锚点窗口）走 `*OnMainThread()` 系列，它们是 internal 的，
并且自带一次运行时断言，一旦违规就写进诊断记录。

**为什么卡片可见性要探测五次而不是等一个固定时间？**

`addView()` 返回时窗口还没走过第一帧布局，`width`/`height` 都是 0。只等一个固定时长就下结论，
设备一忙（比如正在启动游戏）就会误判成"不可见"，白白发一条降级通知。
现在是热 0 / 350 / 800 / 1600 / 2600 ms 阶梯探测，任意一次通过即算成功。

**为什么不加 `QUERY_ALL_PACKAGES`？**

不需要。`<queries>` 里声明 MAIN/LAUNCHER intent 就能拿到所有带启动图标的应用，
这正好是分类页需要的全部信息。而 `QUERY_ALL_PACKAGES` 在 Google Play 属于敏感权限，
在 F-Droid 那边也会被追问。

**为什么不加 Internet 权限做崩溃上报？**

那会直接摧毁这个项目最大的信任优势。崩溃日志靠用户手动 `adb logcat` 贴到 issue 里就好。
CI 里有一条检查：APK 一旦声明了 `INTERNET` 权限，构建直接失败。

**`ReminderPolicy` 为什么完全不碰 Android API？**

为了能被单独测试。它的输入是“几点、前台是哪个包、属于哪一类”，输出是“该做什么”。
加新规则（比如“连续三天在同一应用超时就更早提醒”）只需要改这一个文件，
不需要动服务、悬浮窗或界面。

**为什么设置存在一个 JSON blob 里而不是十几个 DataStore key？**

字段少、读取频繁、需要整体原子替换。blob 的好处是加字段时不用做迁移，
坏处是并发写会互相覆盖——但本应用只有一个写入方（服务主循环 + 界面），
且都用 `edit {}` 的读-改-写，够用。真要并行写入就需要换 Room 了。

**`START_STICKY` 重启时 intent 是 null，会不会崩？**

不会。`onStartCommand` 里 `intent?.action` 为 null 时直接走到默认分支，
照常 `startForegroundSafely()` + `startLoop()`。但注意这条路径正是
“从后台启动前台服务”的路径，所以锚点窗口必须先建好——见 README 的技术决策第 1 条。

**为什么 `ForegroundAppTracker` 要维护内存状态，不每次现查？**

因为 `queryEvents` 返回的是事件流，长时间停留在同一应用时事件流是空的。
只看查询窗口内最后一个事件会把计时清零。详见 README 技术决策第 3 条。
